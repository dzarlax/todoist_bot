Implementation Plan: Todoist MCP Labels and Subtasks

Approval required before implementation

Task Summary

Extend the Todoist MCP server in this Go service so MCP clients can create, update, and delete Todoist labels, explicitly assign labels through the MCP tool schemas, and work with subtasks by listing, creating, and moving tasks under or out from a parent task.

Current Behavior

  • internal/todoist/server.go registers 7 tools: projects, labels list, tasks list, task create/update/delete/complete.
  • create_task and update_task already copy a raw labels argument into the Todoist payload, but the schema does not declare that argument.
  • get_tasks supports project_id, filter, and limit, but not section_id, parent_id, or label filtering.
  • internal/todoist/client.go has raw wrappers for /projects, /labels, and /tasks, but no label mutation methods and no task move method.
  • Telegram-side task creation already supports labels parsed from #tag and should remain unchanged unless implementation discovers a shared helper is useful.

Desired Behavior

AreaProposed MCP surfaceTodoist API behavior
Label CRUD Add create_label, update_label, delete_label. Keep get_labels. Use POST /labels, POST /labels/{label_id}, and DELETE /labels/{label_id}.
Task labels Declare labels as an array input on create_task and update_task. Pass Todoist label names in the existing task payload field labels.
Create subtasks Add optional parent_id to create_task; optionally allow section_id as adjacent placement support. Todoist task creation supports a parent task identifier for creating a subtask.
List subtasks Add parent_id, section_id, and label filters to get_tasks. Todoist GET /tasks supports these query parameters.
Move subtasks Add move_task with task_id required and optional project_id, section_id, parent_id. Use POST /tasks/{task_id}/move; parent_id: null should be supported if MCP argument handling can represent it cleanly.

Assumptions and Unknowns

  • Todoist API v1 remains the target because defaultBaseURL is https://api.todoist.com/api/v1 and docs in this repo already name REST API v1.
  • Personal labels are in scope. Shared label rename/remove endpoints are not included unless explicitly requested.
  • Deletion of a label removes it from tasks in Todoist. The MCP should expose that clearly but not add custom cascade logic.
  • For moving a task back to top level, we need to verify how mcp-go exposes explicit JSON null versus omitted fields in tool arguments.
  • No database access is needed; this feature is an HTTP API wrapper over Todoist.

Implementation Steps

  1. Add client methods: CreateLabel, UpdateLabel, DeleteLabel, MoveTask, and an expanded task-list query builder.
  2. Add MCP tools for label CRUD with required-field checks: name for create, label_id for update/delete, and at least one mutable field for update.
  3. Declare labels in create_task and update_task schemas, and normalize arguments to []string where possible before forwarding.
  4. Add parent_id and section_id support to create_task; add parent_id, section_id, and label support to get_tasks.
  5. Add move_task to move an existing task to another project, section, or parent. Reject empty moves where no destination field is provided.
  6. Update documentation in English and Russian sections to list the new tools and subtask semantics.
  7. Run formatting and verification; update this plan with the results before reporting completion.

API, Auth, and Deployment Impact

  • API contract changes: MCP clients will see additional tools and richer schemas for existing tools.
  • Auth does not change. All new tools stay behind the existing X-API-Key middleware on /todoist.
  • Deployment does not require new environment variables or migrations.
  • Backward compatibility should hold for existing clients because current tool names and existing arguments remain valid.

Test Plan

  • go test ./... for all unit tests.
  • go vet ./... for static checks.
  • go build ./... to confirm the service still compiles as a deployable binary.
  • Unit tests should assert paths such as /labels, /labels/{label_id}, /tasks?parent_id=..., and /tasks/{task_id}/move.
  • Manual live Todoist API smoke test is optional and should only run if explicitly approved because it mutates real Todoist data.

Manual QA Checklist

  • Start the service locally with test Todoist credentials and API_KEY.
  • Call get_labels, then create_label, update_label, and delete_label against a disposable label.
  • Create a parent task, create a subtask with parent_id, list it with get_tasks parent_id=..., then delete the test task tree.
  • Move a disposable task under a parent with move_task, then move it back or delete it.
  • Confirm Telegram bot behavior for normal message-to-task creation is unchanged.

Risks and Edge Cases

  • Todoist label deletion is destructive for task label assignments. The tool should be plainly named and documented.
  • MCP array argument handling may deliver labels as []interface{}, []string, or another decoded shape depending on client; normalize conservatively.
  • Explicit null support for removing a parent or section may need a separate boolean such as clear_parent if MCP client schemas cannot distinguish omitted from null.
  • Todoist IDs are now string-like in v1 examples; keep all IDs as strings in Go and MCP schemas.
  • Existing docs currently say 7 tools; all copies must be updated together to avoid drift.

Rollback Plan

Revert the MCP/client/documentation changes as one commit or patch. Because this plan does not introduce migrations, environment variables, or persisted local state, rollback is a normal code rollback plus redeploy of the previous image.

Open Questions

  • Should shared-label operations (shared labels rename/remove) be included now, or keep scope to personal labels?
  • Do you want a single generic manage_label tool with an action enum, or separate MCP tools? I recommend separate tools for clearer schemas and safer destructive operations.
  • Should move_task include explicit clear_parent / clear_section booleans if direct null is awkward from clients?

Implementation Result

  • Added Todoist client methods for create/update/delete label, richer task listing, and move_task.
  • Registered 4 new MCP tools: create_label, update_label, delete_label, and move_task.
  • Expanded existing MCP schemas: get_tasks now exposes section_id, parent_id, and label; create_task exposes section_id, parent_id, and labels; update_task exposes labels.
  • Implemented clear_parent and clear_section booleans on move_task to send explicit JSON null without relying on MCP clients to pass null fields.
  • Updated README-style documentation to report 11 MCP tools and describe label/subtask support.
  • Added unit coverage for label endpoints, task structural filters, move endpoint payloads, MCP label/subtask argument mapping, and validation errors.
